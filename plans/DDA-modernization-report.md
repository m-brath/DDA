## Findings

- **F0.1** Local ADDA build recipe established (now in `agents.md`):
  `NO_FORTRAN` (no gfortran on this Mac; only IGT/surface need Fortran — unused by the
  pipeline), FFTW3 from the conda env, manual relink with `-Wl,-rpath` (make cannot append
  LDFLAGS from the command line). Stale Linux `.d` files must be cleaned first.
- **F0.2** ADDA **1.2 vs 1.5.0-alpha3 produce identical results** (sphere case,
  `Qext` equal to 12 significant digits; same auto dipole density 160.664 dpl).
  → The 1.2→1.4/1.5 migration is low-risk for the *numerics*; the risk concentrates in
  option *validation* (e.g. rejected combinations) and output *formats*.
- **F0.3** Independent Mie validation (my scipy Riccati-Bessel helper, cross-validated
  against `miepython` 3.3.1, and B&H energy-conservation tests): ADDA deviates +1.7–2.2%
  on the tiny sphere at its *automatic* grid (2176 dipoles). Proven to be DDA
  discretization, not physics or conventions: forcing `-dpl 320/800` converges
  Qext 6.914e-3 → 6.852e-3 → 6.819e-3 toward Mie 6.793e-3. Baseline gate: `rel < 3e-2`
  in `check_baselines.py`.
- **F0.4** Convention trap discovered while writing the check: ADDA uses Im(m)>0 for
  absorption (e^{−ikr}); classical B&H-style helpers need the conjugated m. Documented in
  `check_baselines.py` docstring. Any future validation code must keep this straight.
- **F0.5** Deviation from plan: pipeline-level (Python) golden outputs could **not** be
  generated with the current stack, because the current numpy-2 env cannot even import the
  scripts (see Phase 1 §1.5). Baselines are therefore at the ADDA-binary level — which is
  actually the more robust reference (pure physics layer).
- **F0.6** ADDA 1.5.0-alpha3 built locally already (Phase 3 groundwork paid off early).

TRO path: `adda_main_control_rndorient.py → adda_sub_control_randomorient.py →

**Config contract:** configs are never imported as modules (except by the SSDB exporter,
`adda2SSDBnetcdf_functions.py:436`); all control scripts inject globals via
`exec('from … import *')` and probe optionality with `'name' in locals()`. The full set of
required config globals per control script is enumerated in §1.4 of the raw audit (kept in
session notes); the inventory of bare globals is what makes the ~140 "undefined name"
linter reports (§1.4) non-bugs.

## 1.2 ADDA options actually used (complete)

- Dynamically (`acf.adda_call` :140–171): `-m <re> <im>`, `-lambda` (µm), `-eq_rad` (µm,
  **radius**), `-eps <n>`, `-orient <α β γ>` (always the config base angles = 0/0/0),
  `-prop <px py pz>` (the per-vertex incidence unit vector), `-dir <ramdrive tmp>`.
- Real habit shapes: `-shape read <file>.adda` (`adda_sub_control_spharmonics.py:167`);
  ellipsoid config: `-shape ellipsoid 1.0 0.5`.
- `static_clo` (configs:205–220): `-store_scat_grid`, `-scat_grid_inp scat_params.dat`
  (1° grid: 181×361), `-scat_matr both`, `-Csca`, `-alldir_inp alldir_params.dat`.
- TRO (`adda_call_randomorient` :862–1038): same minus orient/prop, plus
  `-orient avg <avg_params.dat>` in static_clo; `-Csca`/`-alldir_inp` defined but **unused**
  there.
- Launchers: `srun … adda_1.2/src/mpi/adda_mpi` (:107), `mpiexec adda_mpi` (:113 etc.),
  execution via `posix_spawn.spawn_command(' '.join(cmd))` (shell string, no exit-code
  check §1.6-13).
- **Never used anywhere**: `-pol`, `-iter-solver`, `-maxiter`, `-no_vol_cor`,
  `-mueller-amps`, `-dpl` (commented out) — i.e., the whole Phase-4 tuning surface is virgin.

**Implication for Phase 3:** the option surface the scripts depend on is small and all
options still exist in 1.4/1.5 (verified in `adda/src/param.c`); `-eps` semantics
unchanged. The `-orient avg`+grid incompatibility only affects the old TRO configs —
they use no scat-grid flags, so even the old TRO CLI remains legal in 1.4/1.5. ✔

## 1.6 Latent-bug catalogue (dormant today, must be handled in Phases 2–4)

Ordered by phase relevance (full 38-item audit in session record; here the material ones):

1. **Symmetry path is broken by construction** — two independent blockers:
   a) `adda_sub_control_spharmonics.py:572` (& twin `aoa_functions:1289`):
      `vt.flatten(1)` → ValueError (`flatten` takes no arg) — **triggers exactly when
      `sym_*obj=True`**; b) post-processing `aoa.orientational_avg:1320` unconditionally
      raises `'Symmetry is still under construction'`, and `construct_by_symmetry:1104–1125`
      assumes an array shape never passed. ⇒ **Phase 4 must first fix these two** before
      any symmetry-based speedup is measurable. (Also explains why all configs set flags
      False.)
2. `adda_sub_control_spharmonics.py:99` — `if 'calc_type' in locals()==False:` parses as a
   chained comparison → intended default `'thunder'` never applies. Fix in Phase 2/3.
3. `adda_main_control.py:32–35` else-branch never sets `calc_type` (configs define it —
   silent coupling). Local mode (Phase 3.13) needs an explicit, working branch.
4. `adda_sub_control_spharmonics.py:543` — `gamma = p_orientation_alpha[g_i]`
   (copy-paste; harmless only because both arrays are identical today). Landmine for
   Phase 4 gamma-grid changes — fix first.
5. `adda_sub_control_spharmonics.py:211` — `… or ref_lev<=2` forces **min 3 full ADDA
   icosphere rounds** even after convergence (pure CPU waste; also skews Phase-4 timings).
6. `adda_sub_control_spharmonics.py:694` — `converged==False` no-op (intended `=`).
7. `acf.adda_call` cleanup: `path_name` possibly unbound in `finally` (:274–276);
   ramdrive temp dir + zip bookkeeping fragile.
8. `acf.adda_call_randomorient`: mistral branch never defines `commando`; a **bare
   `except:`** swallows the NameError and the function returns `None`; caller then zips a

10. `adda_sub_control_randomorient.py:153` — TRO output folder encodes the liste **index**

11. `acf.loadmat` (used by all configs for `.meta.mat`) relies on scipy's
    `mat_struct` internals — deprecated, breaks with scipy 2. Migrate to
    `scipy.io.loadmat(..., simplify_cells=True)`-style parsing in Phase 2.
12. Duplicated implementations that must be kept in sync or consolidated: inline α/γ
    averaging (`sub_control:494–670`) vs `aoa_functions:1206–1416` (already divergent);

13. ADDA exit codes never checked anywhere (`spawn_command` ignores them; bare excepts in

Key findings:

- **F1.1 Shape resolution scheme**: every size exists in **5 shape resolutions** with
  `frequency_min ∈ {192, 337, 457, 671, 887} GHz` (dipole count tied to fmin; N fixed per
  shape file — ADDA does *not* resample at higher f, it just rescales geometry; effective
  dpl therefore *grows* with f). Cost of a (size,f) job ⇒ set by the shape's
  `N_dipoles`, i.e. by the smallest resolution ≥ f/192 class.
- **F1.2 The three queued configs are test stubs** (single 5 GHz frequency) and
  **HexPlaAgg's current config (175.3 GHz) would not compute a single case** (below every
  fmin). Production frequency plans must be re-enabled/restructured before Phase 5 —
  plan a *frequency-class-aware* driver: for each f, use the shape resolution with
  `fmin ≤ f < next fmin` (this is already what `adda_main_control.py:135–158` skips toward).
- **F1.3 Size caps mostly work**: with `size_parameter_limit=10`, the HongPlate grid keeps
  1078 valid (size,f) pairs and excludes only 146 by x>10 (largest sizes at highest f).
  Note each of the 5 resolution files per physical size is a separate `shapelist` entry —
  the `f<fmin` skip logic already implements resolution selection:
  per frequency ≈31 physical sizes remain active.
- **F1.4 Estimated scale** (for Phase 4/5 planning): HongPlate grid = 1078 (size,f) pairs
  × 3 T = **3234 jobs**, each currently 5β × 10 incidence = 50 ADDA solves
  → ≈162k solves for one habit. The symmetry + incidence-angle optimizations (§1.6-1)
  dominate the cost picture.
